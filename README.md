# Interval Merge Code Evaluation

A project evaluating **20 custom implementations of one function**: `merge_intervals(intervals)`. Each candidate is written as a standalone Python module in `candidates/`. A harness built strictly with the Python standard library runs two executable test suites against every candidate, and a fixed eight criterion rubric evaluates code quality. Automated test results and rubric scores are recorded independently and are never combined into an arbitrary single score.

This is a focused evaluation environment rather than a general benchmark framework: one task, one specification, one manifest, and one test runner.

## Task Specification

The regression suite directly enforces the specification rules defined below.

Implement `merge_intervals(intervals)`:

1. **Input shape:** `intervals` must be a `list`. Every item must be a two element `list` or `tuple` in the form `[start, end]`.
2. **Endpoints:** Every endpoint must be a finite `int` or `float`. Booleans, NaN, and positive or negative infinity are not valid endpoints.
3. **Validation:** Raise `ValueError` if `intervals` is not a `list`, if any element is not a two element list or tuple, if any endpoint violates rule 2, or if `start > end` for any interval. Equal endpoints (`start == end`, a point interval) are valid. Validate the entire input before processing; any invalid entry must trigger a `ValueError`.
4. **Closed ranges:** Intervals are closed `[start, end]`. Two intervals merge whenever `next_start <= current_end`, meaning touching endpoints also merge.
5. **Result:** Return the union of closed ranges as a minimal list of disjoint intervals sorted by start, then by end.
6. **Output shape:** Return a `list` of two element `tuple` objects. An empty input returns `[]`. A single interval returns one tuple, such as `[(2, 5)]`.
7. **No mutation:** Never mutate the input `intervals` list or any nested elements, including when validation raises an exception.
8. **Exact endpoints:** Retain original endpoint values without conversion. Large `int` endpoints must remain exact integers rather than being coerced into floats.

## Layout

| Path | Description |
| --- | --- |
| `candidates/` | 20 candidate implementations (`c01` to `c20`), one module each |
| `data/manifest.csv` | One row per candidate: algorithmic approach, target status, intentional defect, and implementation notes |
| `data/rubric_scores.csv` | Qualitative scores across the eight criteria based on manual code review |
| `tests/cases.py` | Shared case tables (public and regression suites) and test runner logic |
| `tests/test_public.py` | Public test suite using pytest, parametrized across candidates |
| `tests/test_edge_cases.py` | Edge case regression suite using pytest |
| `scripts/evaluate.py` | Evaluation runner using only the Python standard library |
| `rubric.md` | The fixed 100 point qualitative grading rubric |
| `results/` | `results.json` generated by the test runner |
| `reports/` | `summary.md` generated by the test runner |

## Quickstart

Requirements: Python 3.10+

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python -m pytest                         # runs both test suites across all 20 candidates
python -m pytest tests/test_public.py    # public suite only
python -m pytest tests/test_edge_cases.py -q   # regression suite only

python scripts/evaluate.py               # outputs results/results.json and reports/summary.md

```

The only external dependency is `pytest`, which powers the test runner. The evaluation script in `scripts/evaluate.py` relies exclusively on the standard library.

## Test Suites

* **Public suite** (`tests/test_public.py`): Verifies standard functional behavior, including empty lists, single intervals, standard merges, sorting order, duplicates, touching boundaries, negative and floating point values, return types, input immutability, and basic validation errors.
* **Edge case regression suite** (`tests/test_edge_cases.py`): Targets boundary conditions, such as single point intervals, chained overlaps, nested ranges, identical intervals, mixed numeric types, high precision integers, malformed pairs, inverted ranges, non finite floats, boolean flags passed as numbers, invalid outer structures, and mutation safety during failed validations.

Both test suites are fully accessible in this repository with no hidden checks. Both `pytest` and `scripts/evaluate.py` invoke identical cases via `tests/cases.py` to guarantee consistent verification.

## Implementation and Evaluation Notes

* I authored and curated the 20 implementations in `candidates/` to test varied algorithmic structures: classic sorting approaches, stack aggregations, sweep line logic, and recursive variations.
* Eight of the implementations include deliberate, seeded defects (such as failing on point intervals, mutating inputs in place, or improper boolean coercion) to verify that both the test suite and the grading rubric properly catch nuanced errors.
* Each candidate is documented in `data/manifest.csv` alongside its intended algorithmic behavior and defect status.
* Code quality was scored by conducting manual reviews for all 20 implementations using the standards set in `rubric.md`.

### Adding New Implementations

To evaluate an additional candidate implementation:

1. Add the Python file to `candidates/` following the naming format `cNN_approach.py`, ensuring it defines `merge_intervals(intervals)`.
2. Add a corresponding entry in `data/manifest.csv` detailing the implementation approach and authoring notes.
3. Conduct a code review against `rubric.md` and record the scores in `data/rubric_scores.csv`.
4. Run `python scripts/evaluate.py` to regenerate the test reports and evaluation summaries.

## Rubric vs. Automated Tests

The criteria in `rubric.md` allocate 100 points across eight qualitative dimensions:

* Specification correctness (30)
* Edge case handling (20)
* Input validation (10)
* Algorithmic complexity (10)
* Immutability (5)
* Readability and structure (10)
* Type hints and documentation (10)
* Standard library and style restraint (5)

The runner presents results in two independent sections:

* **Automated results:** The exact count of passed and failed test cases per candidate.
* **Rubric scores:** The qualitative points assessed during manual review.

## Scope and Considerations

* Test results evaluate candidates strictly against the contract specified above.
* Algorithmic complexity is assessed directly through static analysis and code review rather than wall clock execution benchmarks.
* Rubric scores represent qualitative evaluations based on the defined scoring guide.
